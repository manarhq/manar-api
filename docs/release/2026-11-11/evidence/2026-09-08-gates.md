### Two failures found and fixed during this run

Both are recorded because they are the kind of thing that is easy to
quietly absorb:

1. **A real regression, caught by e2e.** `test/auth.e2e-spec.ts`'s "an
   expired token is rejected" began returning 200. Cause: a 30-second
   `clockTolerance` added alongside the JWT audience/algorithm fix. The
   test issues a 1-second token and asserts a 401 after 2.5 seconds, so any
   tolerance worth having necessarily defeats it. **The tolerance was
   removed, not the assertion** — see `src/auth/jwt-auth.guard.ts`'s doc
   comment for the reasoning, and the unit test that now pins its absence.
2. **An intentional contract change, so the test was rewritten.**
   `test/app.e2e-spec.ts` asserted `/health/ready` returns exactly
   `{ status: 'ok' }`. That endpoint now reports per-dependency state. The
   test was rewritten to assert the _contract_ — including the
   load-bearing invariant that an unhealthy **optional** dependency must
   still yield `ready: true` — rather than a fixed body, because the body
   legitimately varies with what is running.

### Environment caveat that affected the run

Six e2e failures in the first pass were all one environmental cause:
the host disk is at **95% used**, so OpenSearch crossed its flood-stage
watermark and applied a `read-only-allow-delete` block to
`manar-audit-events`. Every audit-indexing, audit-search, SSE and
audit-investigate test then failed with `cluster_block_exception`.

Resolved by raising the cluster's disk watermarks (transient setting) and
clearing the index block. **No data was deleted and no volume was
removed** — this workspace records a prior incident in which another
project's Docker volumes were destroyed during disk cleanup, and that class
of action stays out of scope.

Worth carrying forward: a developer stack that silently goes read-only
under disk pressure will produce exactly this confusing failure pattern for
the next person. Pinning watermarks in `deploy/docker-compose.yml` is a
candidate follow-up, deliberately not done here as unrelated scope.

## A flaky gate, diagnosed and fixed

The e2e suite initially reported 164/168 with **a different set of roughly
four failures on each run**. Every one of them passed when its file was run
alone.

Root cause: `test/vitest.config.e2e.mts` did not set `fileParallelism`, so
Vitest ran all 27 spec files concurrently against **one shared** Postgres,
Redis, Keycloak, OpenSearch, Kafka and demo-soc-tools. Several tests assert
on global state in those services — most obviously the per-tenant
rate-limit test, whose counters live in the shared Redis, and the
demo-tools integration test, which asserts a specific host is isolated in a
shared process.

Fixed by serialising e2e files, with the reasoning recorded in the config.
Verified with three consecutive full runs at 168/168.

This is worth stating plainly because it was nearly mistaken for a code
regression twice: **a suite whose failures move between runs cannot gate a
release**, since nobody can separate a real regression from the noise.

## Accessibility findings from the design work

Measured, not asserted. All computed by alpha-compositing exactly as the
components render, then applying the WCAG formula.

**Light palette had never actually rendered** (the theme was pinned to dark
with `enableSystem={false}` plus a literal `dark` class), and 10 token/usage
pairs failed AA once it became reachable — the risk badges worst at
**2.01–2.89:1**. Fixed by moving lightness only; hue and chroma unchanged,
`lib/risk.ts` thresholds untouched. Full light audit after: 21 pairs, 0 failing.

**Dark `StatusBadge` `negative` tone failed at 4.01:1.** It could not be
rescued by thinning the fill — `#e14f4f` is only 4.69:1 directly on
`--card`, so every tint sat under that ceiling (/12 → 4.17, /10 → 4.26,
/08 → 4.35). The token moved to `oklch(0.68 0.21 25)`, giving **4.77:1**,
with ramp separation from `--risk-high` preserved (0.094 oklab vs 0.097).
Pinned by `__tests__/status-badge-contrast.test.ts`, which was verified to
**fail at 4.01:1 against the old value** and pass at 4.77:1 with the fix.

A bug in that test is worth recording: its first version located the dark
block with `indexOf(".dark")`, which matched a mention inside a comment and
sliced from above `:root` — so it measured the **light** palette while
reporting itself as dark. It passed against the wrong palette and would
never have caught the failure it was written for. Now anchored on the
`.dark {` selector.

**Target size (WCAG 2.2 §2.5.8):** every interactive element on `/overview`
was enumerated in a real browser at compact density (the worst case) and
measured. All pass at ≥24×24 after adding a structural
`min-block-size: var(--target-min-size)` floor to the button and menu-item
slots — `button`'s `xs`/`icon-xs` variants computed to 21px at a 14px root
before that. Two standalone links on the overview measured 94.75×16 and
were given the `.tap-target` floor.

## A gate that closed on the final run: RAG tenant isolation

**NOT-RUN** — its three cases skip when OpenSearch is unreachable or
refusing index creation, which was the case while the audit index was
flood-staged read-only. They are deliberately not mocked, because a mocked
OpenSearch cannot prove real k-NN efficient pre-filtering behaviour.

With the cluster healthy they now execute and pass:

So the tenant-isolation property of the vector retrieval layer is now
**empirically verified against a real OpenSearch k-NN index**, not merely
structurally verified by query-body shape. That is a genuine upgrade in the
strength of the evidence, and it is worth noting that it was only available
because the environment was healthy — the same tests were honestly recorded
as not-run a few hours earlier rather than assumed to pass.
